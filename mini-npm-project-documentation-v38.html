پیاده‌سازی Package

در این پروژه هدف پیاده‌سازی یک مدیر پکیج ترمینالی در حافظه می‌باشد که قادر به شناسایی وابستگی‌های پکیج‌ها، انجام صحیح عملیات نصب و حذف و مقاومت در برابر چرخه‌ها و خطاهای احتمالی باشد. قوانین و خروجی مورد انتظار مشخص است؛ طراحی داخلی و نحوه پیاده‌سازی به عهده و خلاقیت خودتان خواهد بود.

01 / PROJECT MISSION

A) معرفی پروژه و اهداف آن

هدف این پروژه، پیاده‌سازی یک مدیر پکیج خط فرمان در حافظه است تا مفاهیم ساختمان داده و گراف وابستگی را در یک سیستم واقعی تجربه کنید. نصب واقعی نرم‌افزار، دانلود از اینترنت و Versioning جزو الزامات پروژه نیست.

i

نحوه مقداردهی Registry در برنامه شما: تعریف پکیج‌ها و وابستگی‌های اولیه را از منطق اصلی برنامه جدا نگه دارید (ترجیحاً با خواندن یک فایل JSON استاندارد به قالب {"pkg": ["dep1", "dep2"]} مانند شبیه‌ساز همین صفحه، یا یک ماژول مقداردهی مجزا) تا در جلسه تحویل بتوان بدون دستکاری کد هسته، برنامه را با یک Registry جدید آزمایش کرد.

02 / CONCEPTUAL ENTITIES

B) موجودیت‌های مفهومی و نقش لایه‌ها

04 / REQUIRED DATA STRUCTURES

D) ساختمان داده‌های الزامی

پیاده‌سازی دستی، جنریک و استفادهٔ واقعی از هر سه ساختمان دادهٔ زیر در هستهٔ برنامه الزامی است. انتخاب جایگاه مناسب برای هر ساختار بخشی از طراحی مهندسی خودتان است و در جلسهٔ دفاع باید دلیل انتخاب خود را توضیح دهید.

REQUIRED 01 / LIST

Linked List

ساختار خطی پویا برای نگهداری مجموعه‌های متغیر بدون محدودیت اندازهٔ ثابت.

REQUIRED 02 / FIFO

Queue

ساختار FIFO برای صف‌بندی و پردازش ترتیبی گره‌ها یا عملیات.

REQUIRED 03 / LIFO

Stack

ساختار LIFO برای مدیریت جریان‌های برگشتی، پیمایش‌ها یا ثبت سوابق.

i

الزام جنریک‌سازی و کاربرد واقعی: هر سه ساختمان داده باید جنریک تعریف شوند (مانند LinkedList<T>، Queue<T> و Stack<T>) و واقعاً در جریان اصلی برنامه به کار بروند؛ تعریف صوری و بدون استفادهٔ آن‌ها قابل قبول نیست.

05 / IMPLEMENTATION RULES

E) قوانین پیاده‌سازی: موارد مجاز و غیرمجاز

هدف اصلی این پروژه سنجش تسلط شما بر پیاده‌سازی و استفاده عملی از ساختمان داده‌ها می‌باشد و نه صرفاً رسیدن به خروجی مشابه. رعایت محدودیت‌های این بخش برای تمامی پیاده‌سازی‌ها الزامی است و بر اساس کد و رفتار برنامه ارزیابی خواهد شد.

ALLOWED / YES

موارد مجاز

  • انواع داده پایه، آرایه‌های معمولی و عملیات استاندارد رشته و ورودی/خروجی
  • ثبت و جست‌وجوی داده‌های Registry با ساختار دست‌ساز یا آرایه ساده
  • استفاده از ابزارهای استاندارد خواندن فایل و JSON صرفاً برای بارگذاری اولیه Registry و بخش امتیازی
  • تعریف کلاس‌ها، ساختارها، توابع و ماژول‌های کمکی بر اساس طراحی دلخواه خودتان
  • ساخت ساختمان داده‌های کمکی دیگر، مشروط بر پیاده‌سازی دستی و رعایت محدودیت‌ها
NOT ALLOWED / NO

موارد غیرمجاز

  • استفاده از پیاده‌سازی‌های آماده برای Linked List، Queue و Stack
  • جایگزینی منطق اصلی با ساختارهای آماده مانند List، Map، Set و Deque
  • به‌کارگیری کتابخانه‌های خارجی برای هسته نصب، حذف یا مدیریت وابستگی‌ها
  • تعریف صوری ساختمان داده‌ها بدون استفاده واقعی از آن‌ها در منطق سیستم
06 / CLI CONTRACT

F) قرارداد دستورهای CLI

برنامه باید یک محیط خط فرمان تعاملی داشته باشد و دستورهای زیر را دقیقاً با همین نام‌ها پشتیبانی کند. تطابق عینی متن پیام‌های خروجی الزامی نیست؛ اما «نتیجه» و «اثر وضعیت» هر دستور باید دقیقاً مطابق جدول F-۱ باشد و هر حالت خطا طبق بخش H مدیریت شود.

جدول F-۱: قرارداد رفتاری دستورهای CLI
دستور و نحورفتار مورد انتظار
install <package>نمایش پیش‌نمایش (جدید / از قبل نصب‌شده)، دریافت تأیید y/n و نصب پکیج و وابستگی‌ها بدون تکرار
remove <package>بررسی مجوز حذف، نمایش پیش‌نمایش (در صف حذف / باقی‌مانده)، دریافت تأیید y/n و حذف ایمن و آبشاری
listنمایش فهرست پکیج‌های نصب‌شده همراه با مشخص کردن وضعیت هر پکیج (نصب مستقیم یا وابستگی)
historyنمایش خط فرمان عملیات موفق (install، remove، install-json، install-file) از جدید به قدیم
helpنمایش فهرست دستورها و نحو اجرای آن‌ها
exit / quitپایان امن برنامه و آزادسازی منابع

برای مشاهده نمونه زنده رفتار دستورها می‌توانید آن‌ها را در شبیه‌ساز ترمینال بالای صفحه آزمایش کنید.

✓

یک نکتهٔ مهم: حفظ یکپارچگی وضعیت هنگام خطا یک رفتار داخلی سیستم است؛ پس آن را با دستور عمومی undo اشتباه نگیرید و نیازی به تعریف چنین دستوری در خط فرمان نیست. در صورت افزودن قابلیت‌های اضافی، نباید جایگزین دستورهای الزامی این بخش شوند.

07 / CORE BEHAVIOR

G) قوانین اصلی رفتار سیستم

ملاک صحت پروژه، رفتار درست سیستم روی گراف‌های مختلف است و نحوهٔ پیاده‌سازی داخلی (الگوریتم و متغیرها) کاملاً به انتخاب خودتان بستگی دارد. تضمین شش قانون زیر الزامی است:

01 / TRANSITIVE

نصب وابستگی‌های چندسطحی

پکیج درخواستی و تمامی وابستگی‌های مستقیم و غیرمستقیم آن در همه سطوح بررسی و بدون ایجاد نسخهٔ تکراری نصب می‌شوند.

02 / REINSTALL

نصب مجدد و ارتقا به مستقیم

نصب مجدد پکیجی که از قبل مستقیم نصب شده بی‌اثر است؛ اما اگر صرفاً به‌عنوان وابستگی نصب شده باشد، بدون ایجاد تغییر در وابستگی‌هایش به نصب مستقیم ارتقا می‌یابد.

03 / SAFE REMOVE

حذف ایمن و آبشاری

پکیجی که صرفاً به‌عنوان وابستگی نصب شده یا همچنان مورد نیاز پکیج نصب‌شدهٔ دیگری باشد، قابل حذف نیست و باید بلافاصله با خطا رد شود؛ با حذف یک پکیج مستقیمِ مجاز، وابستگی‌های بلااستفادهٔ آن نیز به‌صورت آبشاری آزاد می‌شوند.

04 / CYCLE

تشخیص وابستگی حلقوی

وجود چرخه در مسیر وابستگی‌های درخواست باید شناسایی و با نمایش مسیر چرخه رد شود، بدون آنکه وابستگی مشترک با چرخه اشتباه گرفته شود.

05 / ATOMIC

یکپارچگی عملیات (همه یا هیچ)

در صورت بروز هرگونه خطا (چرخه یا پکیج ناموجود) یا لغو عملیات با n، وضعیت سیستم باید دقیقاً دست‌نخورده باقی بماند.

06 / DEDUP

نادیده گرفتن وابستگی تکراری

وابستگی‌های تکراری در تعریف یک پکیج یا Manifest (مانند ["ui", "ui"]) باید نادیده گرفته شده و فقط یک‌بار محاسبه شوند.

دام کلاسیک این پروژه: وابستگی مشترک، چرخه نیست!

صرفاً دیدنِ دوباره یک گره در پیمایش، به معنای وجود چرخه نیست.
✓ SHARED DEPENDENCY (VALID) 
A → B → D
A → C → D

هر دو مسیر به D می‌رسند؛ این حالت کاملاً سالم است. D فقط یک‌بار نصب می‌شود و تا زمانی که حداقل یکی از B یا C باقی باشد، حذف نخواهد شد.

× CIRCULAR DEPENDENCY (INVALID) 
A → B → C → A

در این مسیر یک حلقهٔ بسته تشکیل شده است؛ این حالت غیرمجاز است و درخواست باید با نمایش مسیر چرخه و بدون هیچ تغییر ماندگاری رد شود.

08 / ERROR MANAGEMENT

H) مدیریت خطاها

تمامی خطاهای احتمالی در طول اجرای برنامه باید به شکل صحیح مدیریت شوند و هیچ خطایی نباید باعث کرش برنامه یا نمایش stack trace خام به کاربر گردد.

  • حفظ یکپارچگی وضعیت: در تمامی حالت‌های خطا (از جمله پکیج یا وابستگی ناموجود، وجود چرخه، حذف غیرمجاز، دستور نامعتبر و خطای فایل JSON)، وضعیت پکیج‌های نصب‌شده باید کاملاً بدون تغییر باقی بماند.
  • خطاهای اختصاصی: خطاهای اصلی دامنه (مانند پکیج ناموجود، وابستگی حلقوی، حذف غیرمجاز و دستور نامعتبر) باید به‌صورت خطاها یا Exceptionهای اختصاصی و متمایز پیاده‌سازی و مدیریت شوند.
  • شفافیت پیام‌ها: هر پیام خطا باید نام پکیج یا دستور مشکل‌دار (و در حالت چرخه، مسیر چرخه) را مشخص کند. تطابق دقیق متن پیام‌ها با شبیه‌ساز الزامی نیست.
  • خط خالی و پایان ورودی: خط خالی صرفاً باعث نمایش مجدد prompt می‌شود و دریافت EOF یا خطای خواندن استریم باید به خروج امن معادل exit منجر گردد.
09 / REGISTRY SANDBOX

I) آزمایشگاه Registry در مرورگر

در این بخش می‌توانید Registry نمونه را ویرایش کرده و رفتار دستورها را در ترمینال بالای صفحه روی گراف‌های دلخواه آزمایش کنید. اعمال تغییر در Registry صرفاً برای شروع یک آزمایش تازه، وضعیت نصب و تاریخچه شبیه‌ساز را پاک می‌کند.

برای مثال می‌توانید یک گراف سالم یا گرافی دارای چرخه تعریف کرده و عملکرد آن را بررسی نمایید.

وضعیت شبیه‌ساز

دستورها را مستقیماً در ترمینال بالای صفحه تایپ و اجرا کنید.

No packages installed.
نمونه: با Registry پیش‌فرض، اجرای install app مجاز بوده اما install x به دلیل وجود چرخه رد می‌شود. تغییرات یک درخواست ناموفق هیچ تأثیری بر پکیج‌های نصب‌شده قبلی نخواهد داشت.
10 / OPTIONAL BONUS

J) قابلیت امتیازی: نصب از JSON

پیاده‌سازی این بخش اختیاری است و صرفاً پس از تکمیل الزامات اصلی توصیه می‌شود؛ امتیاز آن مازاد بر نمره اصلی پروژه محاسبه می‌شود.

دریافت وابستگی‌ها از Manifest

برنامه باید قادر باشد از یک متن یا فایل JSON معتبر، فهرست وابستگی‌های معرفی‌شده را خوانده و آن‌ها را در قالب یک درخواست یکپارچه نصب نماید. ریشهٔ Manifest یک شیء JSON دارای کلید dependencies است که مقدار آن می‌تواند آرایه‌ای از نام پکیج‌ها یا شیء نگاشت نام پکیج به رشته نسخه باشد؛ مجدداً مدیریت واقعی نسخه‌ها جزو الزامات پروژه نیست.

install-json <manifest>install-file [path]

پکیج‌های Manifest به ترتیب درج در آرایه، یکی‌یکی پردازش می‌شوند (وابستگی‌های تکراری نادیده گرفته می‌شوند) و اگر آرایه خالی باشد ([])، بدون پرسش y/n و بدون ثبت در تاریخچه پیام مناسب نمایش داده می‌شود. فرمت نامعتبر، پکیج ناموجود یا وجود چرخه باید منجر به شکست کل درخواست با حفظ یکپارچگی کامل گردد. مسیر پیش‌فرض install-file فایل package.json است.

BONUSامتیاز تشویقی

نمونه‌ای از ساختار Manifest. تمامی قواعد بخش‌های F تا H (از جمله پیش‌نمایش و تأیید تعاملی y/n، ترتیب درخواست‌ها و یکپارچگی کامل) در این بخش نیز برقرار است.

{
 "dependencies": ["ui", "logger"]
}
11 / IMPLEMENTATION & DELIVERY

K) نکات پیاده‌سازی و تحویل

  1. سورس کامل و قابل اجرا را همراه با README (نحوه کامپایل/اجرا و دستورها) و راهنمای فنی کوتاه (شرح معماری MVC، دلیل انتخاب جایگاه هر ساختمان داده و تحلیل پیچیدگی عملیات اصلی) تحویل دهید.
  2. استفاده واقعی و جنریک از هر سه ساختمان داده دست‌ساز (Linked List، Queue و Stack) در مسیر اصلی برنامه الزامی است.
  3. استفاده از ساختارهای آماده کتابخانه استاندارد زبان (مانند List، Map، Set و Deque) برای منطق اصلی پروژه مجاز نیست.
  4. تمامی خطاهای بخش H باید مدیریت شوند و هیچ خطایی نباید باعث کرش یا باقی ماندن وضعیت نیمه‌کاره گردد.
  5. تعریف اولیه Registry باید از منطق هسته جدا باشد تا در جلسه دفاع بتوان برنامه را روی یک Registry جدید آزمایش کرد.
  6. تمامی حالت‌های عادی و مرزی (نصب چندسطحی، تبدیل وابستگی به نصب مستقیم، نصب مجدد بی‌اثر، حذف آبشاری، چرخه، وابستگی ناموجود و لغو) را پیش از تحویل آزمایش کنید و با تسلط به تمامی بخش‌های پروژه، آمادگی کامل برای ارائه و دفاع از طراحی خود را داشته باشید.
